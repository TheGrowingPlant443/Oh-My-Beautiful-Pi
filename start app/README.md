# OMBP Start app

An independent Linux and macOS launcher that builds the selected checkout without patching its sources. Its local browser UI remains outside the sandbox; isolated OMBP, its private session bus/keyring, and every OMP child run inside **one rootless Podman container**. On macOS that container runs in a dedicated, launcher-owned Linux VM, not directly on the Mac.

## Run

From the repository root:

```sh
cd 'start app'
nix --extra-experimental-features 'nix-command flakes' run path:.
```

The Darwin package also contains `Applications/OMBP Start.app`. It invokes the immutable controller wrapper, so Finder does not need a login-shell PATH. From `start app`, build it with `nix --extra-experimental-features 'nix-command flakes' build path:.` and open `result/Applications/OMBP Start.app`. Keep installed application links backed by Nix GC roots. Intel Darwin uses a separately locked Nixpkgs 26.05 base because 26.11 dropped that platform, while retaining the pinned Lima 2.2.0 recipe and noVNC 1.7.0 assets.

The launcher opens its four-column UI in your browser. On macOS that is always an installed Google Chrome, or else Chromium, Microsoft Edge or Brave Browser, from `/Applications` or `~/Applications` (`/usr/bin/open -a <bundle>`), never Safari or the system default browser, which stays unchanged. The isolated display viewers open the same way. Without such a browser the launcher prints an error and keeps serving. If automatic browser opening is unavailable, open the loopback URL printed in the terminal. Keep that URL private: its fragment authenticates permission changes. A browser reload retains authentication in that tab's session storage.

The control UI intentionally uses authenticated HTTP on loopback, with Host/Origin checks and no cross-origin access. It installs no host certificates. Do not expose it through a port forward or reverse proxy.

Choose the **OMBP source folder** containing the parent `flake.nix`. It defaults to `--source-dir /absolute/checkout` when given, else the source of the last launch that reached running (`last-launch.json`), else the launcher's working directory (or its parent when launched from `start app`) if that is a checkout; otherwise the field starts empty and you choose one (as when started from Finder). Each **Start OMBP** click runs `nix --extra-experimental-features 'nix-command flakes' build path:.#default --no-link --print-out-paths --print-build-logs --no-write-lock-file` in that checkout, so a fresh Nix needs no global configuration change, and launches only its returned `bin/omp-manager`. Local saved changes are included, Nix reuses unchanged build results, and the existing lock file is not updated. This does not fetch or merge another branch, install a profile package, or fall back to an older executable when the build fails. Select the checkout containing the changes you want.

Choose **Podman · isolated** (**Podman · Linux VM (isolated)** on macOS) or **Normal · unrestricted host access**, then Start. Start is accepted at once (`POST /api/start` answers `202 {"operation_id": …}`); one launcher-owned worker prepares, builds and starts it, with phases shown in status. Build output and errors go to `launch.log` as they are produced; every launcher-owned `nix build` uses `--print-build-logs`. **Stop** cancels pending builds and launch children; a late build completion never launches. Closing the launcher also waits for retirement. Builds happen outside the application container (in the VM for macOS isolation, on the host otherwise) and may download Nix dependencies regardless of the website whitelist. Choose only trusted source checkouts. Normal mode uses your native host environment: **none of the whitelist controls apply**.

**Show progress** (next to the status, which is clickable too) opens a live view of the current or last launch: phase, current step, start time and elapsed time, and the operation's part of `launch.log` (VM boot and provisioning, Nix downloads and builds, package installation, container start), refreshed every second while open. It stays available after a failed or stopped launch. Each slow step writes one `==> <step>` line to `launch.log` (for example `==> Booting Linux VM`, `==> Building guest runtime (first run downloads its Nix closure)`, `==> Building OMBP (omp)`, `==> Starting container`); while a launch is in progress the latest step is also shown beside the status. Status reports the operation's `log_start` byte offset and `operation_started` time; the authenticated `GET /api/log?after=<offset>` returns `{"start", "end", "text", "truncated"}` for the log bytes from `max(after, log_start)` to the current end, at most the last 256 KiB (`truncated` when capped), so clients poll with `after=<previous end>`.

**Automatic start** (next to Stop) starts OMBP as soon as the launcher starts, through the same launch phases. Turning it on saves the current settings; afterwards each launch that reaches running updates it, except that an unrestricted (Normal) launch never replaces isolated automatic start. A failed automatic start shows its error in the UI. Turning it on in Normal (unrestricted) mode asks for confirmation.

**Agent** chooses **omp** ([Oh My Pi](https://github.com/can1357/oh-my-pi), `.#default`) or **omsp** ([Oh My Striped Pi](https://github.com/TheGrowingPlant443/oh-my-striped-pi), `.#omsp`, with its own bundled SDK/Bun). The choice reaches OMBP as `OMBP_AGENT`. Both agents use the private `/home/sandbox/.omp` in isolated mode, initialized from the full host copy described below. A checkout missing the selected output fails without fallback.

Both container modes use the matching agent SDK and Bun shipped by the selected OMBP build, rather than installing a mismatched second agent version. Installed mode provides a directly usable `omp` or `omsp` command in `/installed-programs` and points `OMP_BIN` there. Inspection mode sets OMBP's existing `OMP_BIN` hook to this launcher's `/launcher/omp` entrypoint, which runs `src/cli.ts` from OMBP's own `OMP_SDK_DIR` with its bundled Bun. The selected checkout must expose `agent-omp` and `agent-omsp` for installed mode. No OMP process runs on the host for an isolated launch.

### Private OMP state: copy once

On **both macOS and Linux**, the first isolated Start copies the entire local `~/.omp` into `/home/sandbox/.omp`. On macOS this lives on the owned Linux VM's disk; on Linux it lives under the launcher's private `home/.omp`. Container `HOME` is `/home/sandbox`. The host `~/.omp` is **never a bind mount** and is never written back. Normal (unrestricted) mode still uses native host state.

This is a filesystem copy, not a Git export, clone, pull, fetch or filtered checkout. It includes regular files in `.env`, `docs/`, `.git`, caches, runtime directories and arbitrary custom folders, including ignored/untracked files, configuration, extensions, credentials, sessions and database contents. Standalone Git repositories retain their history, branches, index and dirty working tree. No source content is excluded by its name, except the coherent SQLite sidecars described below. File modes/executable bits, modification times and literal symlinks are preserved; host ownership and extended attributes are not transported. Hardlinked file contents become independent private files.

**Later starts retain every container change.** Stop and wait for OMBP to finish, then choose **Copy again on next Start…** to replace that private copy at the next isolated launch. The active `.omp` becomes `.omp.previous`; confirmation explicitly authorizes permanently replacing any older `.omp.previous` backup. The initial copy also preserves any preexisting private `.omp` as `.omp.previous`, rather than silently treating it as already copied. An existing backup is not discarded without explicit Copy again authorization. If the host source is absent, the first copy is empty and this is reported; creating host state later still requires Copy again. The authenticated `POST /api/omp-copy` accepts exactly `{"replace_previous":true}` while idle and queues this action; status reports `omp_copy_pending`.

Each queued Copy again action has a durable request ID carried through the local/VM transaction and receipt. Repeated control requests while it is pending keep that ID. After interrupted publication or a lost VM acknowledgement, retry recognizes the already-applied ID and clears the pending request without copying again or rotating `.omp.previous` a second time. A later, newly confirmed action gets a new ID.

**Copied credentials are visible to the container and AI.** This includes credentials stored in regular files and SQLite databases under `~/.omp`; it does not import the host OS Keychain, Secret Service, SSH agent, or files outside that tree. Copying a token does not guarantee it remains valid, portable or independent of host keychain encryption. Keep the private home and `.omp.previous` confidential. Host-keyring Authorization injection remains a separate opt-in feature.

SQLite databases are identified by their header, not their filename. A separate read-only helper takes SQLite's standard Unix/POSIX database and WAL locks, captures a coherent private DB/WAL/journal image, then uses SQLite's online backup API against that private image. This includes committed WAL data without opening the host database writable or changing its WAL index. Only sidecars belonging to recognized SQLite databases are omitted from the transported tree; their committed contents are already in the backup, and SQLite recreates its transient journals/indexes privately. This requires the standard Unix locking VFS and a filesystem with working POSIX advisory locks, not a custom SQLite VFS. Other regular files are copied as observed; pause unrelated writers when you need cross-file consistency.

The launch log names each SQLite database as capture begins and reports lock contention every two seconds. A browser using exclusive profile/database locking can hold its lock for its entire lifetime, even with no tabs open: close that browser/profile before starting a copy. A capture retries SQLite lock contention or sidecar replacement for at most 15 seconds, then fails with the relative database path and instructions to close the owning application and retry **Start**. Permission errors fail immediately rather than being retried as locks. No credential database is skipped and no incomplete copy is published; the queued recopy request remains usable. If an application removes source files while copying (including a browser shutting down), let it finish and retry **Start**; disappearing entries fail explicitly rather than silently producing a partial tree.

Symlinks are preserved, never followed outside the source. Absolute or external links may dangle in the different container filesystem; their targets are not implicitly granted or copied. Sockets, FIFOs and device nodes cannot become live endpoints across the copy and are explicitly counted as skipped in `launch.log`, along with external-link and SQLite counts. Linked-worktree `.git` references, `.git` symlinks or Git object alternates outside the copied tree fail with an actionable error instead of leaving a silently broken repository. Use a self-contained local repository; the launcher never fetches missing objects.

Local Git history/status/branch/commit operations use the private copy. **Git push still needs usable authentication and permitted network access.** Credentials or SSH keys outside `~/.omp` are not imported, and macOS SSH agents are not forwarded. HTTPS remotes must pass the website gateway and its trust configuration; direct SSH remotes do not bypass the container's `--network=none`. A copied remote URL alone does not enable pushing.

Snapshots stage outside the writable sandbox home, validate archive paths and symlink parents, and publish before launch under a copy lock with a crash-recoverable receipt. Destination links planted by the sandbox are never followed for new writes. Cancellation abandons incomplete staging; publication is a short recoverable commit. On macOS a session-owned capability stages the SSH stream, and only its idle supervisor may commit the verified digest. Existing private state is not refreshed merely because the launcher or VM restarts.

Linux host prerequisites: local rootless Podman, `/dev/fuse`, a host setuid `fusermount`/`fusermount3`, Nix and an existing Wayland session for a graphical launch. The Linux closure supplies Python, FUSE, proxy, compositor and session tools. macOS needs Nix and hardware virtualization; its host closure supplies Python, Lima and OpenSSH, not macFUSE, XQuartz or Wayland. Linux execution prerequisites are provisioned only inside its owned VM. Raw host X11 is never exposed.

### macOS Linux runtime

Choose **Podman · Linux VM (isolated)** on macOS. **Prepare Linux runtime** (`POST /api/prepare` with `{}`, returning 202 and an operation ID) boots and prepares the VM without starting OMBP. Opening the control UI or using Normal mode does not boot it. Before preparation, Add program is disabled; after preparation the catalog lists Linux Nix executables installed in the VM, tagged with `aarch64-linux` or `x86_64-linux`. Native Mac apps and Darwin Nix executables cannot be selected as isolated programs.

The reservation is shown before first creation and saved atomically in `vm.json`: `{"cpus":6,"memory_gib":10,"disk_gib":64}` on a 16 GiB/12-CPU Mac. CPUs default to `min(6, host CPUs)`; smaller Macs reserve host memory minus 4 GiB, with 8 GiB host memory minimum. Edit that exact three-field file only while the VM is stopped. Memory must leave at least 4 GiB for macOS, disk must be at least 32 GiB, and existing disks cannot shrink. These minimums do not promise that every optional quality workload fits concurrently.

Lima 2.2.0 uses Virtualization.framework and the host architecture. Its private `LIMA_HOME` is `~/.local/share/ombp-lima/<state-id>` (`state-id` is the first 12 SHA-256 hex digits of the canonical launcher state path); its instance is `runtime`. Matching owner-only receipts record a random ownership generation, full state path, architecture and image digest. A mismatching receipt is an error, never permission to adopt or delete another machine. No existing Docker, Podman or Lima machines are changed. Global `_config/default.yaml`, `override.yaml` and `base.yaml` files in that private home are refused.

The self-contained template has zero host-directory mounts, both containerd modes disabled, no forwarded SSH agent or X11, no extra host SSH keys, no inherited proxy environment, and explicit ignore-all TCP/UDP forwarding. The controller checks Lima's effective configuration before boot. Ubuntu 24.04 images and the Nix 2.35.4 installer are pinned by mandatory SHA-256 digests. Provisioning installs only bootstrap packages, rootless/FUSE prerequisites, a persistent user session and guest kernel limits; Ubuntu's unprivileged-user-namespace restriction is relaxed only in this dedicated guest when its probe requires it. `/var/lib/ombp/provisioned.json` records that guest-only change.

The guest supervisor raises only its own soft `RLIMIT_NOFILE` to at least 65536, preserving the hard limit and failing actionably if that limit is insufficient. FUSE retains file descriptors for mapped Nix libraries across application and browser processes; Ubuntu SSH's default soft limit of 1024 caused Chromium/Bun library and font failures in physical testing. Raising the verified supervisor's limit, without changing its container or permissions, allowed the same headed Chromium/CDP connection to succeed. No macOS descriptor limit or sysctl is changed.

The locked SonarScanner CLI image is `linux/amd64` only. ARM guests therefore use the launcher's pinned static QEMU x86-64 user interpreter, registered **only inside this owned Linux guest**, with binfmt's `F` flag (not the privilege-preserving `C` flag). It changes neither Mac Rosetta nor host binfmt settings and adds no privileged installer image or engine API. The interpreter must pass executable/static-ELF and actual execution checks before registration; its registration has its own root-owned receipt. The Nix static-musl build uses a non-PIE interpreter to avoid broken static-PIE startup: that executable's mapping is not ASLR-randomized, and emulation adds attack surface and CPU cost inside the VM. The exact three-image engine filter remains unchanged.

The controller deploys its **own launcher sources and lock** and builds `guest-runtime` inside the VM. Every isolated Start separately snapshots the selected checkout's current saved files, including uncommitted/new source, excluding VCS data, worktrees and build/dependency caches. Snapshot extraction rejects escaping links, unsafe archive paths and special entries. OMBP builds inside the VM, never from an old successful output after a failed build. Builds/provisioning have guest networking; the application's rootless container still has `--network=none`, and its inspected proxy and revocable host-file broker remain on the Mac.

**Agent state starts as a full host copy, then stays independent:** isolated OMP/OMSP configuration, credentials and sessions persist in the guest's private home. The Mac's `~/.omp` is copied once, never mounted, and later starts retain guest edits; use **Copy again on next Start…** for an explicit replacement. Linux follows the same private-copy semantics. Software rendering is the only VM GPU mode. The desktop checkbox controls viewer publication, not the private headless compositor needed to run Tauri.

Host folder/network changes apply immediately. Program/requirement projections have desired and acknowledged generations in status; an unacknowledged change retires only the isolated workload, with verified-owned-VM shutdown if retirement cannot be confirmed. Stop cancels pending builds, applications, display and broker capabilities but retains the VM disk and agent/quality data. Closing the controller also shuts down its VM; ordinary cleanup never deletes it.
Cancelling initial VM preparation also stops the verified owned VM, so a disconnected SSH bootstrap command cannot keep provisioning or building in the background. A successfully prepared, idle VM otherwise remains available until the controller closes.
Owned SSH connections also watch their controller's kernel parent relationship and retire on controller death. Guest restart recovery holds an exclusive supervisor lock and removes only owned, unreachable engine socket inodes left by a crash; live listeners, unexpected files and symlinks are refused rather than adopted.

Physical Apple Silicon verification has exercised VM boot, zero host-directory mounts, absent SSH agent/X11 forwarding, disabled TCP/UDP automatic forwarding, repeat idempotent provisioning, guest-runtime build and framed catalog/status RPC. A real reverse-forwarded file broker denied before grant, allowed read-only reads, denied writes until Write was granted, and denied subsequent reads through an already-open handle after revocation. Both OMP and OMSP built and reached a first mapped surface; OMSP's actual matching Bun loaded its ARM native addon. Hidden-desktop startup produced no viewer or VNC process. Approved HTTPS succeeded, denied HTTPS returned 403, and direct public TCP/DNS and host-loopback probes failed from the real container. A real filtered Community/PostgreSQL/CLI scan completed with a passed quality gate under guest-only x86-64 emulation; its services were stopped with data retained. Live provider/model interactions, other optional integrations and Intel VM graphics are separate acceptance checks, not implied by these results.

Installed mode was also exercised on Apple Silicon: the guest built the matching agent and only the selected `package-*` outputs, and the live container mounted just that generation's store and commands read-only, with no `/allowed-programs` and `--network=none`. Selected debugpy Python, Flutter's Dart and ast-grep's `sg` won their command names. A selection saved mid-build did not change the admitted launch, and Stop during package realization left no container or partial generation. An identical restart reused its generation; an empty selection started without browser display or trust. The real Zenity picker opened at `/host/` over the whole output, and `OMBP_GIT_DISCOVERY_HOME` was the Mac home under `/host`. Live folder revocation, internet-off and inspection-mode bundle revocation still applied. The guest agent had no provider login, so no live model interaction was part of this check.


For development or headless control:

```sh
nix develop path:.
python3 app.py --no-browser --state-dir /absolute/private/state
nix build path:. path:.#checks.x86_64-linux.syntax --no-link
PYTHONDONTWRITEBYTECODE=1 python3 -m coverage run -m unittest discover -v
python3 -m coverage xml
```

Python coverage is imported from `.quality-coverage/python.xml`; browser V8 smoke coverage uses `.quality-coverage/javascript.lcov`. Reports and bytecode are excluded from the Nix application source. Coverage tooling is supplied only by the development shell, not the shipped runtime.

The default state directory is `${XDG_STATE_HOME:-~/.local/state}/ombp-start`; on macOS it is `~/Library/Application Support/ombp-start`, unless the former already exists. If both exist on macOS the launcher refuses to guess and asks for `--state-dir`; state directories are never merged. The state directory is owned by you with mode 0700. It contains permissions, denied history, the latest successful launch settings, the proxy CA private key, the private-keyring unlock key, container/VM receipts and `launch.log`; on macOS the persistent private home itself is in the VM. Never publish it. Transient Unix sockets use an owner-only `ombp-start-<uid>-<state id>` directory; Darwin puts it below canonical `/tmp` (`/private/tmp`), independent of a potentially overlong `TMPDIR`. That directory, state and `~/.local/share/ombp-lima` cannot be granted as folders. Network access receives only the public CA and dedicated proxy socket directory. Closing the controller stops its workload and owned VM; closing a browser tab does not. Stop retires the workload without deleting persistent data. Only one launcher may own a state directory, and recovery verifies ownership before retiring recorded resources.

State protection uses the canonical physical directory, including when a parent directory is reached through a symlink. A symlink used as the state directory itself is rejected.

## Installed or inspection mode

**Install into container** is on by default, including when opening existing launcher state. **Choose tools…** opens a modal with optional CLI tools, applications and local language servers. Save persists the selection; Cancel/Escape discards the draft. Changes apply on the next Start, including automatic start; an admitted launch keeps the mode and packages it started with, and its status reports them. Selecting no optional packages is valid: OMBP, the selected agent, Bash/sh, Python, D-Bus/keyring, coreutils, fonts, Podman and the Zenity file picker remain mandatory. Application runtime dependencies such as Bun, Node and Git are also always included. Normal mode never installs or builds packages.

**Keyboard layout (macOS):** Choose tools also has **Keyboard in the OMBP window**, with **Current (US English)** as the default and **Danish**. The VM viewer sends the characters you type; the display's VNC server turns them back into keys of one layout, and characters that layout lacks (æ, ø, å on the US layout) are dropped. Pick the layout of the keyboard you type on. Like the tool selection it is saved on Save and applies to the next Start, for both the OMBP window and the browser window. A Linux host's nested desktop already follows the host session's layout, so the choice is not offered there.

Installed mode realizes the chosen pinned Nix packages where the container runs — on macOS inside the owned Linux VM, never on the Mac — then copies their complete runtime closures into a private installation under that backend's state directory (in the VM on macOS). It never mounts the entire Nix store. The private store and `/installed-programs` are mounted read-only inside the container; program files there do not pass through the permission filesystem. Copies use reflinks where the filesystem supports them; the VM's ext4 disk does not, so each generation there is a full copy (several GiB) using the VM's configured disk. Identical selections reuse their generation. A changed selection, or a changed OMBP/agent build, gets a new generation, so deselected optional packages do not remain merely because they were installed before. Only one generation is kept: once the new one is published the superseded ones are deleted, as is staging abandoned by a killed launch, so a new generation temporarily needs room beside the old one. Transitive dependencies may still provide additional executables: package selection is not a per-binary security policy.

Package realization can download dependencies before the sandbox starts; no host profile is modified. The running container keeps `--network=none`, the existing website proxy policy and live host-folder permissions. Local tools/LSPs do not become hosted services, but project dependency downloads still require the existing network permissions. Required package files are immutable; private home/tmp remain writable.

Turn **Install into container** off to use the original **inspection mode**. Saved program grants and Revoke/Restore selections are retained for that mode, not applied to installed package files (including the **Approved Nix runtime files** switch); folder and network permissions apply in both modes. Its filtered Nix-store and `/allowed-programs` views keep recording denied program lookups. In installed mode a program's **+** opens Choose tools; it neither installs immediately nor clears the unresolved denial. Package and history-filter changes are not permission changes: they never alter a running workload's acknowledged permission projection.

For another machine, share this repository—not your state directory, `~/.omp`, caches, tokens or profiles. The friend supplies the Linux or macOS prerequisites above, their own source folder and tool selection, and their own provider login/model configuration. Installed mode uses pinned Chromium and optionally pinned Obsidian rather than discovering a personal Chrome/Obsidian. Unfree-license choices are marked and off by default. The launcher may already cache tools for inspection mode, but only the selected package closures and mandatory runtime are copied into an installed generation.

### Local tool catalog

The chooser covers all 55 language-server definitions shipped by OMP 18.20.3 and OMSP 18.13.3, including their CLI-based linters. Some share one package, such as the VS Code HTML/CSS/JSON/ESLint servers. It also offers the agents' diagnostic/checker commands, toolchains, debugger adapters, FFmpeg/ffprobe, web-extraction helpers and local terminal tools. Hover a choice for its executable names. A fresh launcher state pre-selects only Basic CLI tools, Chromium, GitHub CLI and OpenSSH; every language server, compiler and other choice is opt-in. Existing saved selections are kept as they are. Choices are offered for the isolated Linux system: on Apple Silicon that is `aarch64-linux` in the VM, available before the VM is prepared, never macOS packages.

Server packages include their required runtime dependencies and essential analysis toolchains. TypeScript's native compiler is packaged so the SDK discovers its native LSP; the JavaScript-based server remains available for older project SDKs. Selected Python with debugpy takes precedence over the core Python command; selecting Flutter takes precedence over standalone Dart; ast-grep's `sg` takes precedence over util-linux's unrelated `sg`. JavaScript debugging receives the packaged adapter path in `JS_DEBUG_DAP_SERVER`. ElixirLS is compiled during the Nix build, not installed by Mix at startup; Ruby LSP inherits its packaged gems and leaves server-gem updates to Nix.

These installations do not supply every project's libraries, compiler version or platform SDK. Project lockfiles, ESLint plugins, gems, NuGet/Maven dependencies, schemas and similar inputs still belong to the project; downloads remain subject to network permissions. Ruby LSP still validates the project's Gemfile/lockfile and dependencies. Installing an adapter does not configure its debug target or install PHP Xdebug into a target project. Arbitrary shell/MCP commands, host clipboard/FUSE/desktop integration and public tunnel services are not added or granted by the catalog, and choosing a tool does not enable Code quality's optional analyzer.

Known package constraints:

- Swift/SourceKit's matching toolchain is supported on x86_64 Linux; the pinned compiler is broken on ARM Linux, so those choices are disabled there (including Apple Silicon's VM) and rejected by the API. Linux does not supply Xcode/macOS SDKs.
- JetBrains Kotlin LSP, Intelephense, Terraform and Obsidian have unfree licenses. Intelephense premium features still require a separate license.
- Erlang LS is the final archived upstream release, with its matching OTP runtime.
- TLA+ includes its actual language server, matching proof manager, pinned CommunityModules and Z3. Isabelle/TLA+, Zenon, LS4 and SANY remain additional proof-backend requirements.

The shipped CodeLLDB and Ruby debugger definitions need project transport/target settings. For example, a project `dap.json` can contain the following; replace `./main.rb` with that project's Ruby entry point:

```json
{
  "adapters": {
    "codelldb": {
      "args": ["--port", "${port}"],
      "connectMode": "tcp"
    },
    "rdbg": {
      "args": ["--open", "--port", "${port}", "--host", "127.0.0.1", "--command", "--", "ruby", "./main.rb"],
      "connectMode": "tcp"
    }
  }
}
```

## Four columns

Each column's top-right **i** opens keyboard-accessible help. Program and folder suggestions are local: typing does not perform a web search or grant access. macOS uses its native `Movies` folder rather than Linux's `Videos`; explicit XDG folder overrides remain respected.

In the sandbox, file and folder Browse dialogs using Zenity (including SonarQube scanning) start at `/host`, where approved host folders retain their full paths: `/Users/you/project` appears as `/host/Users/you/project`. The sandbox's Zenity entrypoint supplies `--filename=/host/` only when the caller supplies no filename; Normal launches are unchanged. This changes navigation only, not folder permissions.

The OMBP display keeps the main application borderless/fullscreen. Only Zenity dialogs float over the whole output, keeping their **OK** and **Cancel** controls visible without adding a titlebar to OMBP: Linux's nested Weston kiosk shell maximizes them, and macOS's headless Sway applies an exact `app_id` rule and reapplies the output size when the viewer resizes the display. The separate browser display keeps the browser's address bar.

Repository discovery for OMBP's Nix-packaged source walker checks the selected directory, then parents, stopping at the first `.git` marker or home. The container receives `OMBP_GIT_DISCOVERY_HOME` as `/host` followed by the canonical home of the user who owns the host files: on Linux the host home, on macOS the Mac home (never the VM account's home or `/home/sandbox`). This bounds scans of your shared projects; it neither grants parent-folder access nor hides denied attempts. Existing history entries remain until you clear them.

1. **Folder access:** use the common-folder picker or type a name/absolute path in **Host folder**. Search is local and bounded (6 levels, 50,000 entries or 0.3 seconds), skips hidden/dependency/build folders and protected state, and never follows links or executes programs. **Allow write and deletion** sets the remembered default for new grants; each existing grant has its own live **Write** toggle. Write includes deletion. Granted host folders appear under `/host` followed by their absolute path.

   The container workspace is `/tmp/omp-manager`. Its physical host path is granted read/write once: normally `/tmp/omp-manager` on Linux and `/private/tmp/omp-manager` on macOS. At launch the gateway maps that grant to the container workspace. Revocation applies live; a grant first added after launch is available only under `/host` until restart.

   **Private OMP state on both backends:** the full host `~/.omp` is copied once into `/home/sandbox/.omp`, including credentials, Git metadata and custom files. Ordinary restarts preserve the private copy; **Copy again on next Start…** explicitly replaces it and rotates `.omp.previous`. This is persistent private state, not a revocable host mount. See **Private OMP state: copy once** above for backup, SQLite, symlink and Git-push details.

   Other private sandbox mounts retain separate Revoke/Restore controls applied on the next launch; revoking required resources can prevent startup. The private home is required for the OMP copy. Gateway-shared host folders retain their symlink, hardlink, system-tree and private-state protections.
2. **Programs & desktop:** installed mode lists the required core and the current package selection; use **Choose tools…** and restart to change it. A row whose name is underlined contains several programs (for example **Required installed core** or **Basic CLI tools**): click it to list them. After a Start the list shows the exact commands installed then; before that it shows the package's main commands. In inspection mode the required bundles open the same list. Inspection mode also lets you search installed Nix applications or enter a Nix executable path. On macOS these are Linux programs in the prepared VM, not Mac applications. Suggestions never execute desktop commands. Extra programs appear in `/allowed-programs` with their Nix dependencies and can be added/removed live; their heading lines up with **Host folder grants** in the Folder access column. Required OMBP/runtime bundles are remembered; Revoke denies their primary store roots even if another bundle references them, and may break OMBP. Already loaded code cannot be taken back. This is a **host-resource whitelist, not a ban on arbitrary code inside the container**. Linux can detect/select AMD or NVIDIA devices (NVIDIA requires CDI); macOS offers software rendering only. Display/GPU changes require a new launch.
3. **Websites & internet:** **Turn on internet for the container**, below the URL field, defaults on for a fresh state; existing on/off choices are preserved. It enforces the whitelist unless **Allow all network traffic** (Denied attempts) is on. Four removable defaults are seeded once: GitHub, Google, Stack Overflow and Atlassian. Removed defaults do not return on restart. Type a URL or domain in **Enter a URL** (no suggestions), then click Allow website. Bare domains gain `https://`. **Subdomains** is on by default for each site: `github.com` also allows `api.github.com`, over http or https on default ports, and a leading `www.` is ignored, so `www.google.com` allows `*.google.com` (including `http://clients2.google.com`); a site entered with an explicit port only covers that exact scheme and port; untick Subdomains for exactly the listed origin. Redirects to unrelated origins still need their own entry. Host keyring Authorization is only ever sent to the exact origin. Add/remove and the internet switch apply live; active proxy streams are revoked on the gateway's 250ms policy check. Whenever permissions change (or the launcher starts), denied website rows that are now allowed are removed from Denied attempts.
   **Auto-approve** (on by default) lets through matching hosts over http or https. The first time an origin is auto-approved it is added to the website list as an ordinary entry (Subdomains on), so you can see and manage it; removing it there does not stop auto-approve from letting it through again. An entry with a dot, such as `google.com`, matches any host that **contains** `google` and ends in `.com`, so `www.google.com`, `clients2.google.com` and `update.googleapis.com` pass, but `google.de` does not. An entry without a dot, such as `openai`, matches any host containing it. Defaults: `anthropic.com`, `chatgpt.com` and `google.com`. Containment is deliberately broad: `google.com` also matches a look-alike such as `evilgoogle.com`. Untick it to stop; **Settings** shows the entries with **−** each and an Add field. Each allowed site also has two opt-in dependency checkboxes:
   - **HTML/CSS** allows every origin that site's own served HTML and CSS load as resources (scripts, stylesheets, images, fonts, media, frames, CSS `url()`/`@import`); plain links are ignored. The proxy learns these from responses as you browse, so the sandbox cannot forge them. Dependencies that scripts request later are not covered. Sites that embed user-chosen resources (for example images from any host) widen the list.
   - **Header** allows any origin requested with that site in its `Origin`/`Referer` header, which also covers script-loaded dependencies. **Any program in the sandbox can fake that header, so while it is on, the sandbox can reach any website.**
   Approved dependency groups appear under their site with their own **−** to remove them together.
4. **Denied attempts:** **Allow all network traffic** at the top switches the website whitelist off (it asks first and turns red while on; click again to stop). Anything in the container can then reach any public website, so readable files can leave; private networks and host loopback stay blocked, and **Turn on internet** still overrides it. Gateway-observed denied folders, programs and websites have a **+** action; program actions depend on the container mode as described below. Approved folder/website rows disappear from the list and reappear only if denied again. Denied websites are grouped under the site whose served page loaded them, or else the site named in the request's `Origin`/`Referer` (grouping only; you still approve). Expand a group to see each blocked website with a checkbox (all checked by default); the group's **+** allows the checked ones as that site's dependencies, removable later as a group under the site in the Websites column. Unapproved HTTPS destinations are denied after TLS interception so the requesting site is visible; nothing reaches them. **Clear history** clears the saved history without granting permissions; new attempts, including previously cleared resources, appear again. The latest 500 distinct resources are retained. Direct network syscalls and missing programs outside the gateways have no reliable target history here.

In installed mode the program **+** opens package selection for the next launch; only inspection mode grants programs live. Folder quick-add uses the saved **Allow write and deletion** default, not a separate permission rule.

OMP and OMSP probe supported language-server commands, which can produce many denied program lookups in inspection mode. **Hide language-server denials** (on by default, saved with the permissions) filters program entries matching their 55 configured command names and shows how many entries are hidden. It does not change permissions or delete history. Unticking restores the entries. Matching uses the command name, not its caller or arguments, so other uses of shared commands such as `tsc` or `deno` are hidden too; folder and website denials remain visible. A login shell's `-bash`-style lookup is not a program name and is never recorded.

The container's `/tmp` (**Private temporary files**) starts as a private in-memory filesystem, discarded on stop — not your host `/tmp`. The read-only root filesystem needs this writable scratch space for D-Bus, compilers and other tools. Separately, the default `/tmp/omp-manager` host grant can be mounted over that subdirectory through the permission gateway.

If denied-history storage fails, permission enforcement continues and current events remain in memory. The history column shows a warning until a later save succeeds. Failed permission saves remain errors and do not change the effective permissions.

The container has no external network interface. A loopback proxy relay connects to a host Unix socket. Clients that ignore proxy settings cannot bypass the whitelist; their requests fail. HTTPS is terminated and re-encrypted by mitmproxy with a launcher-local CA, and upstream certificates remain verified. CONNECT destination, SNI, request authority and Host must agree. DNS is checked for non-public addresses and pinned before connection, blocking private networks and rebinding. Each upstream connection stays on its vetted IP but is pooled under its hostname, so keep-alive requests reuse it (policy is still checked per request); without that, the sixth request to one host waited forever behind five idle connections and pages such as the ChatGPT login never finished loading. WebSockets to allowed origins work (for example ChatGPT's) and are cut when the origin or internet is revoked; other HTTP upgrades and raw tunnels are rejected. Certificate-pinned clients fail closed; trust/proxy environment variables are supplied for common Python, Node, Bun, curl and TLS clients, but an application may require its own proxy/CA configuration.

Unfinished uploads remain revocable after an early upstream response, including a rejected protocol-upgrade response. Registered exchanges are retired only after both messages finish, or after an error or disconnect.

**In-container loopback is allowed:** `localhost`, `*.localhost`, `127.0.0.1` and `[::1]` bypass the website proxy. With `--network=none`, these addresses reach only the sandbox's own processes, including OMBP's browser helper and the dedicated SonarQube relay. **Host loopback remains blocked.** Exposing the host's `127.0.0.1` would expose services that may trust local clients: this launcher's control UI, SonarQube on 9000, OMP's RPC listener, CUPS on 631, Podman services and local AI servers such as Ollama on 11434, LM Studio on 1234 and llama.cpp on 8080. Depending on each service's authentication and capabilities, that can expose credentials or permit host-side actions and sandbox escape. The SonarQube relay is the only explicit loopback-service exception.

## Default tools and Code quality

Chrome trusts the whitelist gateway's CA through a launcher-generated private NSS database, not a host trust-store change or a certificate-verification bypass. The database is recreated at each container start and mounted at the private home's `.pki`; it is writable because Chrome requires read-write NSS initialization. Custom NSS imports there do not persist. The sandbox's existing `.pki` files remain underneath the mount and are not overwritten. Host trust tools never reopen this database after exposing it to the sandbox.

The private container hostname stays stable across restarts, and each OMBP terminal's browser profile lives in the persistent private home, so logins (for example GitHub) are remembered across browser and launcher restarts. Engine archive staging uses the sandbox's private temporary filesystem, including clients that discard `TMPDIR`.

**Browser window:** OMBP's Browser button looks for google-chrome-stable, google-chrome, chromium, chromium-browser, chrome and brave-browser. In the sandbox all six names belong to the default **Sandbox browser window** requirement, so none show up as denied. Each name opens the real sandbox browser (your Google Chrome, or launcher Chromium when Chrome is absent; `brave-browser` is not real Brave) in a **second nested desktop window** that the launcher opens on first use and closes when the last browser exits, so the browser no longer covers OMBP. That display maximizes instead of fullscreening (a small pinned Weston kiosk-shell patch), so Chrome keeps its tabs and address bar. Revoking **Isolated desktop socket** also removes that window; browsers then share OMBP's display.

Startup speed: Nix-store files are immutable, so the permission filesystem lets the kernel keep their page cache between opens (each open is still authorized), and the sandbox reads the browser package once in the background after OMBP starts. Measured here: first Browser click about 6 s (was about 15 s), reopening about 5 s.

The following removable program-bundle descriptions apply to inspection mode; installed mode uses the modal selections and mandatory core described above.

Removable requirements include your installed Nix **Google Chrome** (launcher Chromium if Chrome is absent), **Obsidian** when installed, **gh**, **ssh**, **python**, **dbus-daemon**, **sh/bash** (the sandbox shell), the **Podman client**, and **Basic tools**: gdbus/gio/gsettings, notify-send, zenity (OMBP's file and folder pickers fall back to it because the sandbox has no desktop portal), ps/pgrep/pkill/kill/free/top (procps), killall/fuser (psmisc), util-linux (column, flock, setsid, …), find/xargs, grep, sed, awk, diff/cmp, patch, file, which, less, tar/gzip/bzip2/xz/zstd/zip/unzip, curl, wget, jq, rg, fd, rsync, tree, make, bc, strace, lsof and clear/tput. They only run inside the container: host files still pass the folder gateway and network still passes the website gateway, and with all capabilities dropped and no-new-privileges, tools such as mount or su cannot gain privileges. A shell adds no power the sandbox lacks: OMBP, the Terminal and the AI already run arbitrary code inside the container. The sandbox has its own private session bus and a stable random `/etc/machine-id` (not the host's); it has no notification service, so `notify-send` reports that none is available instead of reaching your desktop. No host browser profile or login is imported. Revoke/Restore works like the other program bundles. OMBP's detected **bundled-libsecret** requirement exposes `secret-tool` through `/allowed-programs`; it uses the private session D-Bus and keyring, never the host's credential store. The Terminal uses the sandbox's Bash. Code quality's prerequisite check looks for Podman first and for Docker only when Podman's client is absent or Docker is the selected runtime; inside the sandbox it uses Podman through the filtered **SonarQube engine** connection.

The Basic tools bundle includes **Marksman** (`marksman server`) for Markdown; **Emmet Language Server** (`emmet-language-server --stdio`) for HTML/CSS abbreviation completion; **TypeScript Language Server** and **TypeScript** (`typescript-language-server --stdio`, `tsc`); **VS Code's extracted language servers**, including `vscode-html-language-server --stdio`; the Nix language servers **nil** and **nixd**; and **Eclipse JDT Language Server** (`jdtls`) with its Java runtime. These provide language-specific assistance for OMP/OMSP rather than being required for basic file editing. OLS, Vim Language Server and Docker language servers are not bundled.

The **SonarQube engine** folder requirement exposes a filtered API, never the unrestricted host Podman socket. It permits OMBP's `omp-q-*` objects with the launcher's ownership label, the three pinned Community/PostgreSQL/CLI-scanner images, named owned volumes, internal networks and a single host-loopback SonarQube publication. Host bind mounts, host namespaces, privileged containers and other engine routes are blocked. Community + CLI scanning is supported; Maven/Gradle/.NET/custom-image modes are not allowed by this image filter.

SonarQube and PostgreSQL run in separate host rootless containers: a SonarQube crash does not stop OMBP. First launch seeds a Community configuration using connection `ombp-engine`, port **9100**, and manual Start; existing Code quality settings are left untouched. The user's host analyzer on port 9000 is not changed. The sandbox forwards only its configured SonarQube loopback port through a dedicated socket. Revoke the engine requirement and restart to disconnect it; stopping the launcher does not delete SonarQube's persistent data. In the macOS VM the same filtered gateway, pinned images and SonarQube relay run against the guest's own rootless Podman. That engine is never the Mac's Podman or Docker, and its volumes persist on the VM disk.

No additional website permissions are seeded for these tools. `gh` needs the appropriate GitHub origins and a login inside the sandbox. The SSH tools are available locally, but arbitrary outbound SSH is not supported by the HTTP(S)-only gateway.


## Credentials

For external credential injection, create an entry in your **host** credential store. On Linux use the Secret Service keyring:

```sh
secret-tool store --label='OMBP API' application ombp-start origin https://api.example.com
```

On macOS use the login Keychain. The service must be `ombp-start` and the account the exact origin:

```sh
/usr/bin/security add-generic-password -U -s ombp-start -a https://api.example.com -l 'OMBP API' -w
```

With `-w` last, `security` prompts for the value instead of taking it from the command line; `-U` updates an existing item. An item created this way trusts `/usr/bin/security`, which the launcher runs for lookups, so reading it needs no confirmation. You can instead use **Keychain Access → File → New Password Item…** with Keychain Item Name `ombp-start` and Account Name the exact origin; then add `/usr/bin/security` under the item's **Access Control**. Without that, macOS asks for permission on every lookup, and the launcher fails closed after 5 seconds. Remove an entry with `/usr/bin/security delete-generic-password -s ombp-start -a https://api.example.com`. The launcher only runs the fixed `/usr/bin/security find-generic-password -s ombp-start -a <origin> -w`. No other Keychain items match, and the value never appears in arguments, the environment or logs.

At the secure prompt enter the complete `Authorization` value, such as `Bearer …`; do not put the value in shell arguments, chat or this repository. Add that base URL in the UI with **Attach Authorization from host keyring** checked. Injection requires **HTTPS** and the origin must match exactly, including any non-default port. To change the choice, remove and re-add the website.

The host gateway looks up and injects the header only for that approved origin, after validating its destination. The container gets neither the stored value nor access to the host keyring socket or Keychain. Missing, locked, denied and malformed credentials all fail closed with the same generic error. A credential or website revoked while a lookup is still running is not injected. This does **not** stop the AI exercising that origin's approved privileges, or a trusted upstream deliberately echoing credentials in its response. Do not enable injection for an untrusted service.

On macOS the isolated application runs in the app-owned Linux VM, but the website gateway still runs on the Mac. It uses the Mac launcher's Policy, CA and Keychain. The VM receives only the gateway's Unix socket, reverse-forwarded by the controller's own SSH connection and alone in the directory mounted at `/network`, together with the public CA certificate. The CA private key, Mac Keychain and control token stay on the Mac. The guest checks that the forward is live before the container starts. It has no gateway or CA of its own to fall back to, so the sandbox loses website access as soon as the run's forward or gateway stops.

If an Authorization-based client refuses to make a request without a local API key, configure a non-secret placeholder in its private container configuration; the gateway replaces the outgoing Authorization header. This does not support providers that require an `x-api-key` header or an interactive OAuth flow instead.

Alternatively, the container has its own persistent home and private Secret Service daemon. Its keyring is initialized and unlocked automatically using a random per-state key stored on the host in owner-only `keyring-unlock.json`. That key is delivered once over stdin, never mounted or put in arguments/environment; no host login password is imported. Back up the unlock key and private home together. An existing non-empty private home without its key is refused rather than silently rekeyed. On macOS the key stays in the Mac launcher state, and the controller delivers it through the VM management channel. The guest stores only a SHA-256 verifier next to the private home and refuses any other key for that home; this verifier is initialized before the first OMP copy. On both platforms OMP uses the independent private `/home/sandbox/.omp`, initially copied in full from the host. Credentials given to OMP, copied from host files/databases, or retrieved from this private keyring can be seen by the AI. Injection does not provide arbitrary custom-header/OAuth flows or populate OMBP's model configuration.

## Desktop and GPUs

On Linux, desktop output uses a host-side **nested Weston compositor**, rendered with Pixman. Only its client socket is mounted; the host display socket, clipboard, screen/input protocols, session bus and portals are not exposed. OMBP appears in a separate desktop window. The helper watches the launcher process lifetime and exits if it dies. This intentionally does not provide host-desktop automation, which could escape the filesystem/network boundary by controlling a host terminal or browser.

The internal display resizes live to the space assigned to that desktop window when it is tiled, resized or maximized. The launcher uses Weston's mature kiosk shell with three small pinned Weston patches: the nested window has no Weston title bar or border, so OMBP gets the entire host allocation; a fullscreen kiosk window larger than its allocation is clipped instead of disconnecting the client; and each client's outgoing event queue may grow to 16 MiB instead of libwayland's 4 KiB default, so moving the mouse over OMBP while it is briefly busy (for example during startup) no longer disconnects it with `Data too big for buffer` and `Process exited 1`. Your host compositor's own border is unchanged. Move the window with the host compositor's normal shortcuts. Closing it (for example Super+Q) stops OMBP and its container like the launcher's Stop button, without reporting a crash. Allocations below OMBP's 720×480 minimum keep running but are clipped, not shrunk or downscaled. Native popups and focus handling remain Weston's kiosk implementation. No container restart or OMBP patch is needed.

**macOS VM displays:** Weston cannot serve VNC, so inside the app-owned Linux VM each display is a headless, Pixman-rendered **Sway** compositor (`vm_display.py`) with no key bindings, bars, Xwayland, swaynag or window frames; OMBP fills the output, Sway floats dialogs, and the browser keeps its tabs and address bar. Each display has a private runtime directory (Sway IPC, wayvnc's control socket and configuration) and a public directory holding only a hard link to its Wayland socket (plus the browser display's `request.sock`); only the public one is mounted into the container. The compositor is always created because OMBP needs one. **Show OMBP in an isolated desktop window** additionally starts **wayvnc** on guest loopback, which the Mac controller forwards over its own SSH connection to a private Unix socket; with it unticked there is no VNC listener, forward or viewer. Starting succeeds only once OMBP maps its first window within 30 seconds of the container starting. After that, closing OMBP's last window stops the run, and if the compositor or VNC server dies, the run is stopped and reported as a display failure. The browser display starts on the first browser request, like on Linux, and closes when the last browser exits. All display processes exit when the guest supervisor does. Rendering is software-only: GPU passthrough is refused in the VM.

The Mac side (`viewer.py`) serves the pinned noVNC 1.7.0 client library (`core/` and `vendor/` only, not noVNC's own UI) on its **own** `127.0.0.1` port, separate from the control UI. Each display generation gets a random 32-byte credential carried in the URL fragment. The page removes it from the address bar and history, then offers it as the WebSocket subprotocol `ombp.<token>` alongside `binary`; only `binary` is echoed. The server checks Host and Origin, compares the credential in constant time, and connects only that display's forward. It keeps no access log. The credential is useless against the control API, and the viewer has no control routes. **Open OMBP** and **Open browser** appear in the control UI while a viewer is live, and the controller opens each viewer when it becomes ready. The viewer asks Sway to match the window size (`resizeSession`) and falls back to local scaling only if the server never negotiates ExtendedDesktopSize. It has keyboard and pointer input but no clipboard bridge, file transfer or power controls. Closing a viewer tab only disconnects it: use Stop, or close OMBP's last window.

Physical Apple Silicon verification rendered both OMP and OMSP in the actual Chrome viewer. OMBP's Browser button opened a second viewer with Chromium's tabs/address bar; keyboard input and navigation worked, and closing its final tab revoked that display while OMBP kept running. Real guest tests additionally exercise mapped clients, compositor/VNC failure cleanup, hidden displays and RFB resize to 1000×700. Host viewer tests cover live WebSocket/Unix forwarding, rejected Host/Origin/tokens, generation revocation and viewer/control credential separation. These checks do not imply that optional external providers or knowledge services have been configured.

**Software rendering (GPU None, the only mode in the macOS VM):** the container receives the pinned Nix Mesa drivers with llvmpipe selected (`LIBGL_ALWAYS_SOFTWARE=1`, `GALLIUM_DRIVER=llvmpipe`) and libglvnd pointed at Mesa's EGL vendor file, because the private store has no `/run/opengl-driver`. Without an EGL display WebKit aborted its web process the first time a page used WebGL, which left OMBP blank and unresponsive when the Dependency tree drew its graph. No device is exposed in this mode.

**AMD (Linux only):** exposes `/dev/dri/renderD*` and, when available, `/dev/kfd`, retaining supplementary device groups and supplying Nix Mesa drivers. It requires functioning host drivers and device permissions and does not install ROCm or application-specific compute libraries. GPU passthrough is not exercised by this Mac verification; Mac isolation supports software rendering only.

**NVIDIA (Linux only):** requests Podman's `nvidia.com/gpu=all` CDI device. It requires a working host NVIDIA driver/toolkit and generated CDI configuration. The launcher does not generate or modify those settings. No NVIDIA hardware was used for this verification.

The application container runs as a non-root UID/GID mapped to the Linux runtime user's UID/GID; on macOS that is the VM user, not the Mac account. Container UID/GID 0 are unmapped. This lets crun set up FUSE mounts as their owner without globally enabling `allow_other`. All capabilities are dropped and no-new-privileges is set. The root filesystem is read-only, with a private writable home and temporary directories. No unrestricted Podman/Docker socket, host PID/network/IPC namespace, session bus or keyring socket is shared.

Chrome retains its own user-namespace sandbox; no `--no-sandbox` wrapper is used. Podman's default seccomp profile blocked Chrome's zygote on this machine, so the outer container uses **`seccomp=unconfined`** while retaining dropped capabilities, no-new-privileges, private namespaces and the filesystem/network gateways. This removes the outer syscall filter and increases kernel attack surface. Nix Chrome/Electron wrappers are told to use the nested Wayland display, not a host X server.

## Host-folder enforcement

`host_files.py` is the launcher's single implementation of folder permissions: grant selection, protected launcher paths, descriptor-relative no-follow traversal, revalidation of already-open handles against the current path, inode, link count and policy, denial deduplication and rename bookkeeping. On Linux the FUSE gateway (`access_fs.py`) presents it as `/host`; the `/store` and `/programs` views, Nix closure resolution and page-cache behaviour stay in the gateway.

Protected paths on macOS are checked against no-follow filesystem identities, not just text prefixes: changing case or Unicode normalization cannot expose launcher state or allow renaming one of its ancestors. Reserved private directories that do not exist yet use their nearest existing ancestor's identity and that volume's reported case-sensitivity. Distinct names on case-sensitive volumes remain distinct, and Linux's case-sensitive grant matching is unchanged.

`file_broker.py` serves the shared folder enforcement over a private, owner-only Unix socket, reverse-forwarded by the Mac controller to its VM. No host directory mount or host-file TCP listener exists. Frames have a four-byte length and at most 1 MiB JSON; bytes use base64 chunks of at most 64 KiB. Open modes are semantic booleans and errors use symbolic errno names. Handles are opaque and connection-bound. The entire server is bounded to 16 established connections, 64 outstanding requests, 4096 handles and 64 directory cursors; opening more connections cannot multiply those budgets. Handle and cursor slots are reserved before filesystem operations, including opens that may truncate. Every request rechecks host policy, including already-open handles; disconnect closes its handles and cursors and subsequent guest operations fail with IO error, never local-path fallback. Links, device nodes and ownership changes are refused.

Directory pages enumerate incrementally instead of retaining complete directory snapshots on the host. Each page examines at most 4096 entries (including hidden or denied names), has a bounded encoded size, and retains at most one pending name with its directory descriptors. Revoking a broad grant while retaining a narrower child grant invalidates the old cursor rather than revealing former siblings. Folder/private-path changes and directory identity replacement also invalidate it; only a fresh listing may use the new authority.

Linux pins each inspected object with `O_PATH` and reopens exactly that inode through `/proc/self/fd`. macOS has neither, so its implementation opens the inspected leaf relative to its pinned parent with `O_NOFOLLOW|O_NONBLOCK` and without truncation, then requires the same device and inode, a regular single-link file (or directory) on the grant's device, before any truncation or IO. A path or inode swap therefore fails safely instead of redirecting data or truncating another file. The backends are not syscall-equivalent:

- **Device-swap limit:** if another host process replaces an inspected file with a device node between that inspection and the open, the open itself can reach the device driver before the identity check rejects and closes it. No data is read, written or truncated through it, and the sandbox cannot create links or device nodes.
- Mode changes, time changes and fsync always go through a descriptor of the checked object. An object the launcher cannot open (for example a mode-000 file) cannot have its mode or times changed on macOS; this returns "operation not supported" instead of falling back to a pathname change. Execute-only directories are traversed with `O_SEARCH`.
- macOS privacy controls apply to the launcher itself. When they refuse a folder (for example Desktop, Documents or Downloads), the operation fails with "Operation not permitted" and Denied attempts shows *macOS denied this access*; allow that specific folder for the launcher when macOS asks, or in System Settings › Privacy & Security › Files and Folders. Full Disk Access is not required.

## Security limits

- On Linux, rootless containers share the host kernel. On macOS they share the owned VM's Linux kernel, not the Mac kernel. The VM, compositor, proxy and filesystem gateways still add attack surface; this is not a guarantee against kernel, driver or virtualization exploits.
- Readable files may be sent to any approved website. Writable grants permit deletion and modification; keep backups. Broad folder grants can expose credentials outside the launcher's protected state.
- In gateway-shared host folders, symlinks, hardlinked regular files, special files, ownership changes and nested cross-device mounts are blocked. A nested filesystem needs its own grant. Creating host symlinks/hardlinks is unsupported. These gateway restrictions do not filter the independent OMP copy described above. Some build workflows therefore need a project in the container's own home instead of a writable host mount.
- Revocation blocks subsequent host-file IO and network flows in both container modes, and new program access in inspection mode. Installed package changes apply on the next Start. Neither mode can retract bytes already read, copied files, cached immutable content, loaded code, or data already sent. Stop the container when you need to retire already-running programs.
- Gateway-observed history cannot identify arbitrary denied OS calls. Exhaustive per-tool intent/history, native OMBP credential-provider integration or host-desktop control would require a separate OMBP/broker design; none is silently patched into OMBP here.
- Isolated mode requires rootless Linux Podman and Linux Nix programs. macOS runs these inside its owned VM; Normal mode remains native and unrestricted. No unrestricted fallback, arbitrary remote Podman machine, Windows launcher port, host configuration import beyond the explicit full OMP copy, or host-browser login sharing is included.
